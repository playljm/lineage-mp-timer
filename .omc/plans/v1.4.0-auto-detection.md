# SPEC v1.4.0 — Single-Region Auto ROI Detection

> **Status**: DRAFT
> **Author**: Planner (Claude)
> **Date**: 2026-05-04
> **Baseline**: v1.3.21 (displayId 일치 검증)

---

## 1. Executive Summary

v1.3.x의 OCR 시스템은 사용자가 MP/EXP/Level/ADENA 4개 영역을 각각 픽셀 단위로 드래그 지정해야 한다. 이 방식의 문제:

| 문제 | 영향 |
|------|------|
| 4번의 정밀 마우스 드래그 (5분+ 셋업) | 사용자 진입 장벽, 재지정 피로 |
| displayId 불일치 (멀티 모니터) | anchor 오염 (2026-05-04 실제 케이스) |
| 게임 창 이동/리사이즈 시 절대 좌표 어긋남 | OCR 실패, 수동 재지정 필요 |
| 영역 좌측 4-5px artifact | AutoTrim 거부 -> paddle misread |

**v1.4.0 목표**: 게임 창 전체(또는 큰 영역) 1개만 지정하면 시스템이 MP/EXP/Level/ADENA 위치를 자동 탐지하고, 게임 창 이동을 자동 추적한다.

## 2. Game UI Analysis (Lineage Classic)

리니지 클래식 UI는 고정 레이아웃으로, 각 요소의 위치가 매우 일관적이다.

### 2.1 UI Element Signatures

| 요소 | 위치 (상대) | 시각 특성 | 탐지 전략 |
|------|------------|----------|-----------|
| **HP 바** | 화면 중앙 상단 | 빨강색 가로 막대 (R>>G,B) | Color blob: hue 0-15, sat>60% |
| **MP 바** | HP 바 바로 옆 (우측 또는 하단) | 파랑색 가로 막대 (B>>R,G) | Color blob: hue 200-240, sat>50% |
| **MP 숫자** | MP 바 위/옆 | 흰색/베이지 텍스트 "cur/max" | HP/MP 바 앵커 기반 offset |
| **LEV/EXP** | 좌하단 | 갈색 진행바 + 흰/베이지 텍스트 "LEV:28 EXP 74.1354%" | 갈색 바 탐지 + 텍스트 offset |
| **ADENA** | 우하단 | 노란 원(금화 아이콘) 옆 숫자 | Yellow blob(hue 40-60) + 우측 offset |

### 2.2 Key Constraints

- UI 위치는 게임 창 기준 **상대 비율**로 매우 일관됨 (해상도 무관)
- 창 모드에서 게임 내 UI 재배치는 없음 (옵션 미제공)
- 채팅창/팝업이 일시적으로 UI 요소를 가릴 수 있음
- 게임 클라이언트 버전에 따라 UI 미세 차이 가능 (rare)

## 3. Architecture Design

### 3.1 Two-Phase Pipeline

기존 파이프라인과 v1.4.0 파이프라인을 병렬 모드로 운용한다.

```
[v1.3.x Legacy Mode]
  user picks 4 regions -> captureRegionToCanvas(region) -> OCR -> vote -> apply

[v1.4.0 Auto Mode]
  user picks 1 game-window region
    -> Phase 1: ROI Detection (color blob + anchor-offset)
      -> find HP bar (red) -> find MP bar (blue, relative to HP)
      -> find EXP bar (brown, bottom-left)
      -> find ADENA icon (yellow circle, bottom-right)
      -> derive text ROIs from visual anchors
    -> Phase 2: OCR (reuse existing pipeline)
      -> captureRegionToCanvas(derived ROI) -> same hybrid voting
    -> ROI Cache (skip Phase 1 on subsequent ticks)
    -> Drift Detection (re-run Phase 1 periodically or on failure)
```

### 3.2 Module Decomposition

새 모듈 `src/js/roi-detector.js`를 도입한다. `app.js`에 직접 추가하지 않고 별도 파일로 분리하여 ~6000줄 `app.js`의 추가 비대화를 방지한다.

```
roi-detector.js (신규)
  ├── detectGameUI(canvas)        -- 전체 탐지 엔트리포인트
  ├── findColorBlobs(imageData, hueRange, satMin, minArea)
  ├── findHpBar(imageData, w, h)  -- red blob -> HP bar bbox
  ├── findMpBar(imageData, w, h, hpBar)  -- blue blob near HP -> MP bar bbox
  ├── findExpBar(imageData, w, h) -- brown bar bottom-left
  ├── findAdenaIcon(imageData, w, h) -- yellow blob bottom-right
  ├── deriveTextROIs(anchors, frameW, frameH) -- visual anchor -> text regions
  └── validateROIs(rois)          -- sanity check (size, position, overlap)
```

`app.js` 변경:
- `autoDetect` 객체에 `gameRegion` 필드 추가 (큰 영역 1개)
- `autoDetect.mode` 필드 추가: `'manual'` (기존) | `'auto'` (v1.4.0)
- `runDetectionTick` 분기: `mode === 'auto'`이면 새 파이프라인 사용

### 3.3 Color Blob Detection Algorithm

HSV 컬러 공간에서 특정 hue 범위의 연결 픽셀 군집을 찾는다.

```
function findColorBlobs(imageData, options):
  1. RGB -> HSV 변환 (per pixel)
  2. 마스크 생성: hue in [hueMin, hueMax] AND sat >= satMin AND val >= valMin
  3. Connected Component Labeling (4-connectivity)
  4. 각 component의 bounding box 계산
  5. minArea 이하 component 제거
  6. area 내림차순 정렬
  return [{ x, y, width, height, area, avgHue, avgSat }]
```

**HP 바 탐지 파라미터**:
- hue: 0-15 OR 345-360 (red wraps around)
- saturation: >= 40%
- value: >= 30%
- minArea: frameWidth * 0.03 (바 최소 길이)
- 위치 필터: y < frameHeight * 0.4 (상단 40% 내)

**MP 바 탐지 파라미터**:
- hue: 200-240 (blue)
- saturation: >= 35%
- value: >= 25%
- minArea: frameWidth * 0.03
- 위치 필터: HP bar 기준 y +/- 50px 내 (인접)

**EXP 바 탐지 파라미터**:
- hue: 25-45 (갈색/amber)
- saturation: >= 25%
- value: >= 20%
- 위치 필터: y > frameHeight * 0.85 (하단 15%)
- x < frameWidth * 0.5 (좌측 절반)

**ADENA 아이콘 탐지 파라미터**:
- hue: 40-65 (yellow)
- saturation: >= 50%
- value: >= 50%
- 위치 필터: y > frameHeight * 0.85 (하단 15%)
- x > frameWidth * 0.5 (우측 절반)
- 형상 필터: aspect ratio 0.7-1.4 (원형에 가까움)

### 3.4 Anchor-to-ROI Derivation

시각적 앵커(바/아이콘)로부터 텍스트 ROI를 도출한다.

```
function deriveTextROIs(anchors, frameW, frameH):
  mpTextROI:
    - x: mpBar.x (or mpBar.x - mpBar.width * 0.1)
    - y: mpBar.y - mpBar.height * 2  (바 위쪽 텍스트)
    - width: mpBar.width * 1.2
    - height: mpBar.height * 2
    - fallback: mpBar 영역 자체 + 상단 확장

  expTextROI:
    - x: expBar.x
    - y: expBar.y - expBar.height * 1.5
    - width: expBar.width * 0.6  (텍스트는 바 길이의 일부)
    - height: expBar.height * 2

  levelTextROI:
    - expBar 좌측에서 "LEV:" 텍스트 위치
    - x: expBar.x - expBar.width * 0.15
    - y: expBar.y - expBar.height * 1.5
    - width: expBar.width * 0.15
    - height: expBar.height * 2

  adenaTextROI:
    - adenaIcon 우측
    - x: adenaIcon.x + adenaIcon.width
    - y: adenaIcon.y - adenaIcon.height * 0.3
    - width: frameW * 0.08  (숫자 길이 추정)
    - height: adenaIcon.height * 1.6
```

> **Note**: 위 오프셋은 초기 추정값. 실제 게임 스크린샷으로 보정 필요. 보정 계수는 `roiOffsets` 객체로 분리하여 사용자가 미세 조정 가능하게 한다.

### 3.5 ROI Validation

도출된 ROI가 합리적인지 검증한다.

```
function validateROIs(rois, frameW, frameH):
  for each roi:
    - width > 10px AND height > 5px  (너무 작으면 실패)
    - width < frameW * 0.5 AND height < frameH * 0.3  (너무 크면 실패)
    - x >= 0 AND y >= 0 AND x+width <= frameW AND y+height <= frameH  (경계 내)
  cross-check:
    - mpROI와 expROI는 y 차이 > frameH * 0.3  (MP는 상단, EXP는 하단)
    - adenaROI.x > expROI.x  (아데나는 경험치 우측)
  return { valid: boolean, issues: string[] }
```

## 4. ROI Cache and Game Window Drift Tracking

### 4.1 ROI Cache

Phase 1 (Color blob detection)은 상대적으로 비싼 연산이다. 매 틱(1초)마다 실행하면 불필요한 부하가 발생한다.

**캐시 전략**:
- 첫 탐지 성공 시 ROI 좌표를 `autoDetect.cachedROIs`에 저장
- 이후 틱에서는 캐시된 ROI로 바로 Phase 2 (OCR) 실행
- 캐시 만료 조건:
  - OCR이 N회 연속 실패 (parsed=null) -> 캐시 무효화 -> Phase 1 재실행
  - 사용자가 수동으로 "재탐지" 버튼 클릭
  - 주기적 재검증 (300초마다 Phase 1 재실행하여 캐시 갱신)

```javascript
autoDetect.cachedROIs = {
  mpText:    { x, y, width, height },  // gameRegion 내부 상대 좌표
  expText:   { x, y, width, height },
  levelText: { x, y, width, height },
  adenaText: { x, y, width, height },
  anchors: {
    hpBar: { x, y, width, height },
    mpBar: { x, y, width, height },
    expBar: { x, y, width, height },
    adenaIcon: { x, y, width, height }
  },
  detectedAt: timestamp,
  frameSize: { w, h }
};
```

### 4.2 Game Window Drift Detection

게임 창이 이동/리사이즈되면 `gameRegion`의 절대 좌표가 어긋난다. 이를 자동으로 추적하는 메커니즘이 필요하다.

**접근법: Anchor Re-detection**

매 틱에서 Phase 2 전에 가볍게 HP/MP 바의 위치를 확인한다.

```
function checkDrift(currentFrame, cachedAnchors):
  1. cachedAnchors.hpBar 위치 주변 +-20px 범위에서 빨간 blob 검색 (작은 영역만)
  2. 발견되면 drift 계산: delta = (newHpBar.center - cachedHpBar.center)
  3. delta가 유의미하면 (> 3px):
     - 모든 cachedROIs에 delta 적용
     - cachedAnchors 갱신
  4. 발견되지 않으면:
     - 전체 Phase 1 재실행 (큰 이동 또는 UI 변경)
```

**비용**: 작은 영역(40x40px)에서만 color check -> <1ms. 전체 Phase 1보다 100배 저렴.

**v1.4.0 scope**: 게임 창 이동(translation) 추적만. 리사이즈는 v1.4.x에서 다룬다.

### 4.3 Storage Changes

`storage.js`의 `loadAutoDetect` 기본값에 추가:

```javascript
{
  // ... existing fields ...
  mode: 'manual',           // 'manual' | 'auto'
  gameRegion: null,          // { x, y, width, height, sourceId, displayId, displayLabel, scaleFactor }
  cachedROIs: null,          // Phase 1 결과 캐시 (위 구조)
  roiCacheMaxAge: 300,       // 초 단위, 캐시 강제 갱신 주기
  roiFailThreshold: 5,       // OCR N회 연속 실패 시 캐시 무효화
  roiOffsets: null,           // 사용자 미세 조정용 오프셋 (advanced)
}
```

**마이그레이션**: `mode` 필드 없으면 `'manual'`로 기본. 기존 4영역 데이터 보존.

## 5. Detection Pipeline (Detailed Flow)

### 5.1 Auto Mode Detection Tick

```
async function runDetectionTickAuto():
  1. gameRegion으로 전체 프레임 캡처 (1x, raw — color 분석용이므로 upscale 불요)
  2. ROI 캐시 확인:
     a. cachedROIs 존재 AND 나이 < roiCacheMaxAge?
        -> checkDrift(frame, cachedROIs.anchors)
        -> drift 보정 적용
     b. 캐시 없거나 만료?
        -> detectGameUI(frame)
        -> 성공: cachedROIs 저장
        -> 실패: 에러 표시, 다음 틱 재시도

  3. 각 ROI를 gameRegion 내부 sub-region으로 변환:
     derivedRegion = {
       x: gameRegion.x + roi.x,
       y: gameRegion.y + roi.y,
       width: roi.width,
       height: roi.height,
       sourceId: gameRegion.sourceId,
       displayId: gameRegion.displayId,
       scaleFactor: gameRegion.scaleFactor
     }

  4. 기존 OCR 함수 호출 (captureRegionToCanvas -> hybrid voting):
     ocrMpRegion()    -- autoDetect.mpRegion = derivedRegion.mpText
     ocrExpRegion()   -- autoDetect.expRegion = derivedRegion.expText
     ocrLevelRegion() -- autoDetect.levelRegion = derivedRegion.levelText
     ocrAdenaRegion() -- autoDetect.adenaRegion = derivedRegion.adenaText

  5. OCR 결과 처리 (기존 runDetectionTick과 동일)

  6. 연속 실패 카운터 관리:
     모든 OCR parsed=null -> consecutiveFailures++
     하나라도 성공 -> consecutiveFailures = 0
     consecutiveFailures >= roiFailThreshold -> cachedROIs = null (재탐지)
```

### 5.2 Integration with Existing Pipeline

핵심 원칙: **기존 OCR 함수(`ocrMpRegion`, `ocrExpRegion` 등)는 수정하지 않는다.**

`runDetectionTick`에서 `autoDetect.mode`를 확인하여 분기:
- `mode === 'manual'`: 기존 flow (변경 없음)
- `mode === 'auto'`: 
  1. ROI detection/cache를 통해 `autoDetect.mpRegion` 등을 동적으로 갱신
  2. 이후 기존 `runDetectionTick` 로직 그대로 실행

이 방식의 장점:
- 기존 hybrid voting, stability check, template matching 전부 재사용
- `captureRegionToCanvas`/`captureRegionToRawCanvas` 변경 불필요
- OCR 정확도 개선(v1.3.x의 ensemble/white-extraction)이 auto mode에서도 자동 적용

## 7. Compatibility and Migration

### 7.1 Mode Toggle

- **수동 모드** (기존 v1.3.x): 4개 영역 개별 지정. 코드 변경 없음.
- **자동 모드** (v1.4.0 신규): 게임 영역 1개 + 자동 ROI 탐지.
- 토글로 전환 가능. 수동 모드의 영역 데이터와 자동 모드의 gameRegion/cachedROIs는 독립 저장.
- 자동 모드에서 수동 모드로 전환해도 기존 수동 영역 데이터 보존.

### 7.2 Migration Path

| 버전 | 기능 | 비고 |
|------|------|------|
| **v1.4.0** | Color blob detection + anchor-offset ROI + 캐시 | MVP: 기본 해상도(1024x768, 1280x720, 1920x1080)에서 동작 |
| **v1.4.1** | ROI 미세 조정 UI (offset slider) | 탐지가 약간 어긋날 때 사용자가 px 단위 보정 |
| **v1.4.2** | Drift tracking (게임 창 이동 자동 추적) | checkDrift 구현 |
| **v1.4.3** | 게임 창 리사이즈 대응 (비율 기반 ROI 재계산) | frameSize 변화 감지 |
| **v1.5.0** | Template matching 보강 (HP/MP 바 아이콘 정밀 탐지) | 다양한 게임 클라이언트 버전 대응 |

### 7.3 Backward Compatibility

- `autoDetect.mode` 필드 없으면 `'manual'`로 기본 -> 기존 사용자 영향 없음
- 자동 모드가 ROI를 갱신할 때 `autoDetect.mpRegion` 등을 동적으로 설정 -> 기존 OCR 함수는 이 필드만 참조하므로 변경 불필요
- `storage.js`의 `loadAutoDetect`에 새 필드 기본값 추가 + 마이그레이션 로직

## 8. Known Risks and Mitigations

### 8.1 False Positive Detection

| 위험 | 원인 | 완화 |
|------|------|------|
| HP 바가 아닌 빨간 UI 요소 감지 | 빨간 채팅 텍스트, PK 경고 | 위치 필터(상단 40%) + minArea + aspect ratio |
| MP 바가 아닌 파란 요소 감지 | 파란 장비 아이콘, 스킬 쿨다운 | HP 바 앵커 기반 근접 필터 (y +-50px) |
| EXP 바가 아닌 갈색 요소 감지 | 인벤토리 배경, 채팅 배경 | 하단 15% 제한 + 가로 elongation 검증 |
| ADENA 아이콘 아닌 노란 요소 감지 | 노란 효과, 버프 아이콘 | 하단 15% + 우측 절반 + 원형 aspect ratio |

### 8.2 UI Occlusion

채팅창, 팝업, NPC 대화 등이 OCR 영역을 가릴 수 있다.

**완화**:
- 기존 stability check가 가림 상황에서 자연스럽게 reject (OCR 결과가 불일치)
- 연속 실패 시 캐시 유지 (ROI 자체는 유효, 일시적 가림만)
- `roiFailThreshold`를 넉넉히 설정 (기본 5회 = 5초 연속 실패 시에만 재탐지)

### 8.3 Resolution Variance

- 탐지 파라미터(hue range, minArea, 위치 필터)를 **프레임 크기 비율**로 정의하여 해상도 무관하게 동작
- 테스트 해상도: 1024x768, 1280x720, 1366x768, 1920x1080, 2560x1440
- 극단 해상도(800x600, 4K)는 v1.4.x에서 추가 검증

### 8.4 Game Client Version Differences

- 리니지 클래식 기준으로 설계. 리마스터/다른 버전은 UI 배치가 다를 수 있음.
- 탐지 파라미터를 프로파일로 분리 가능하게 설계 (`roiProfile` 필드, 향후 확장)
- v1.4.0에서는 리니지 클래식 단일 프로파일만 지원

### 8.5 Performance

| 연산 | 예상 비용 | 빈도 |
|------|----------|------|
| 전체 프레임 캡처 (1x) | ~2ms | 매 틱 (auto mode) |
| Phase 1: Color blob detection | ~15-30ms (1920x1080) | 캐시 미스 시만 |
| Drift check (작은 영역) | <1ms | 매 틱 |
| Phase 2: OCR (기존) | ~200-500ms | 매 틱 (변경 없음) |

**결론**: Phase 1은 캐시로 amortize되어 무시 가능. 전체 성능은 기존과 동일.

**Acceptance Criteria**:

- localStorage 마이그레이션: 기존 데이터 -> 새 필드 추가됨 (기존 필드 유지)

### Task 3: ROI Cache + 연속 실패 재탐지
